# Keep class program changes and enrollment writes consistent

## Context

Promotion PR #696 was held after review found that changing a class's program and concurrently enrolling its student in another class could pass separate conflict checks and leave two active enrollments of the same program type in one academic year. The user explicitly authorized fixing this bug, verifying it, then merging staging and promoting to main when all checks pass.

## Spec

- Class program changes and enrollment writes coordinate before reading the program/type used by their conflict checks.
- Whichever request commits first, the second request observes the committed membership/program or returns a retryable conflict; it cannot create a second active enrollment of the same type/year.
- Direct enrollment through either admin entry point, reactivation, and single/bulk promotion participate in the coordination. Existing valid school-plus-daycare and cross-year enrollments continue to work.
- Concurrent enrollments can still proceed when they do not conflict. No schema, dependency, permission, or user-interface change.
- Reuse a tenant-scoped transaction advisory guard: shared for enrollment writers, exclusive for class program changes, always before student-stream/class locks. Refresh or refuse stale preflight snapshots under the guard.
- Existing direct edits to Program.type are outside this class-program regression; do not redesign program administration here.
- Verify both request orders with deterministic real-Postgres barriers, including both direct enrollment endpoints, and run the repository's full local and CI gates.

## Implementation

- Plan: driver=gpt-6, workers=gpt-6; T1 sequential worker implementation, independent standards/spec/security review workers after the patch; driver handles architecture, verification orchestration and merges.
- Scope approved by the user's explicit fix-and-promote request; no additional product decisions required.
- T1: `lib/enrollment/topology-lock.ts` and the class-update, two direct-enrollment, single-promotion and bulk-promotion routes share a tenant-scoped transaction guard. Class moves take it exclusively; enrollment writers take it shared before refreshing their class snapshots and acquiring stream/class locks. Stale snapshots and conflicting target enrollments return 409 without writes. Promotion batches sort stream locks and re-read their source roster before writing.
- Tests: five behavioral API regressions expose the original stale-snapshot behavior; existing enrollment/promotion mocks now include the fresh reads. The new `e2e/class-program-enrollment-race.spec.ts` uses actual HTTP requests and PostgreSQL row barriers for both request orders through both direct enrollment doors, plus valid school/daycare coexistence; fixtures use CRUD and SQL is limited to observing/holding locks and reading invariants.
- The touched single-promotion query used `GROUP BY ... FOR UPDATE`, which PostgreSQL rejects with 0A000. It now locks the target row, then counts its roster in a separate statement. No schema change.
- Independent standards, spec and security reviews cleared the runtime patch. A build caught nullable tenant IDs in the promotion callbacks; both now capture the already-validated tenant ID before entering the transaction.
